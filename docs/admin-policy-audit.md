# Administrative policy audit

Date: 2026-09-09. Read-only audit of the administrative application, privileged agent, backup engine and browser interface at commit `5349b29ede171fe154f399797a20ac557e33f04f`. The production release path and 12-hour session setting were confirmed over SSH. Recommendations below are not implemented changes.

This inventory groups related input and resource checks. It does not claim to audit every Linux, proxy, Minecraft or third-party dependency restriction. Source references are relative to the repository root.

## Sessions and access

| Rule | Current effect | Recommendation | Source |
|---|---|---|---|
| Fixed 12-hour session and cookie expiry | Active use does not renew the session; the user must sign in again. No environment setting exposes this duration. | Persistent, revocable device sessions with renewal and a clear expiry policy. Preserve drafts when authentication is required. | `admin/settings.py`, `admin/store.py:session/current_session`, `admin/app.py:authenticated` |
| Invalid session triggers login immediately | API 401 and stream `session-ended` clear the client session and hide the application. | Explain expiry/revocation and preserve the current task. Ordinary stream connection failure already does not log out. | `public/admin/app.js:api/enter/showLogin` |
| Updating another account revokes all its sessions | Also deletes invitations, disables schedules and cancels queued jobs, even for a promotion or unchanged settings. | Apply side effects only to relevant changes; transfer service-owned schedules instead of silently disabling them. | `admin/app.py:update_user` |
| Owner cannot edit own role/access | Requires a second owner for any such change. | Protect the last active owner, rather than prohibit all self-management. | `admin/app.py:update_user` |
| Last passkey cannot be deleted | Prevents losing the only login method. Removing another passkey does not revoke sessions established with it. | Keep account recovery protection; provide credential/device session revocation. | `admin/app.py:delete_credential` |
| Passkey user verification is required | Browser/device requests biometric/PIN at sign-in or registration. No additional operation-specific reauthentication was found; `verified` is stored but not used as an age gate. | Keep authentication separate from operation confirmation. | `admin/auth.py`, `admin/store.py` |
| Authentication challenge lasts 180 seconds; browser prompt 120 seconds | Challenges are single-use, including a failed verification attempt. | Refresh expired prompts smoothly; retain replay protection. | `admin/auth.py`, `admin/store.py:challenge/consume_challenge` |
| Enrollment invite lasts 15 minutes and is single-use | Expired or consumed links cannot enroll. | Keep single-use; make renewal accessible. | `admin/store.py:invite`, `admin/auth.py` |
| Authentication rate limit is global | 30 authentication endpoint requests/minute across the app process, rather than per client; options and verification both count. | Use scoped limits plus an overall abuse ceiling. | `admin/app.py:boundary` |
| Four fixed roles | Owner alone can delete/restore backups, use console, manage access and grant/revoke game operator status. ## Backup lifecycle and recovery

| Rule | Current effect | Recommendation | Source |
|---|---|---|---|
| Recent/daily/weekly retention uses a union | Default 16 recent, 7 calendar days, 4 ISO weeks overlap. This is not 15 days of 3-hour points. | Configure a time window and interval directly; show actual oldest recovery point. | `admin/backup_repository.py:retention` |
| Latest point cannot be deleted | Applies to manual deletion as well as retention. | Keep automatic replacement protection; allow deliberate owner deletion with clear impact. | `admin/backup_repository.py:delete` |
| Pinned points cannot be deleted | Must first unpin; unlimited pins can exhaust the budget. | Keep explicit pins, expose their total cost and an explicit delete/unpin action. | `admin/backup_repository.py:retention/delete` |
| Last successful boot point is protected indefinitely | A failed/stalled testing pipeline can keep an old point forever; owner cannot directly delete it. | Remove indefinite implicit protection; use a bounded fallback policy. | `admin/backup_repository.py:retention/delete` |
| Cleanup normally runs once per day | Reaching budget prioritizes cleanup only when that daily interval has elapsed. | Cleanup based on upcoming capture needs and storage pressure. | `admin/store.py:tick_backups` |
| Budget is checked before capture | At/above 20 GiB the capture fails. It does not automatically evict retained points until capture fits; a capture can overshoot. | Estimate working space and growth, expire eligible points, reclaim, then retry with bounded behavior. Never erase all recovery history during a failed replacement. | `admin/backup_repository.py:capture` |
| Source itself has a hard-coded 20 GiB ceiling | Increasing repository budget does not lift this independent ceiling. | Replace with available-resource admission and an explicit supported source limit. | `admin/backup_repository.py:capture` |
| Separate 20 GiB disk reserve | Capture additionally requests 2.1 times source size; restore requests 2.2 times expanded size; compaction requires 2 GiB beyond reserve. | Account for actual peak concurrent workspace and make reserve adaptive. Reserve is free space, not stored backup data. | `admin/runtime.py:require_space/restore_archive`, `admin/backup_repository.py` |
| Policy value ceilings | Interval 30–10080 min; recent 2–96; daily 0–90; weekly 0–52; budget 5–80 GiB; checks/tests 1–30 days. 96 recent points cannot express 121 points for a full 15-day window at 3 hours. | Use time-based retention and capacity-derived limits. | `admin/backup_repository.py:validate_policy` |
| Fixed 30-minute automation backoff | Applies after each previous automated job of the same kind, including failure. | Classify failures and retry transient conditions sooner with bounded backoff. | `admin/store.py:tick_backups` |
| Fresh status required for scheduling | No automated scheduling with repository status older than 60 seconds; disabled policy also stops automated checks and cleanup. | Separate capture enablement from repository maintenance and expose stale-state recovery. | `admin/store.py:tick_backups` |
| Consistency and save confirmation gates | Capture requires confirmed flush; stable copy has 8 passes/120-second budget. | Keep consistency guarantees and always resume saves; improve retry/explanations. | `admin/runtime.py:stable_copy`, `admin/backup_repository.py:capture` |
| Structural check required before cleanup | Check failure prevents automatic deletion/compaction. | Keep conservative handling of actual repository damage; provide diagnosis/recovery instead of a dead end. | `admin/backup_repository.py:compact` |
| Global check failure blocks all restores | Even a target that may still be readable is unavailable through the normal flow. | Offer target-specific verification and recovery; do not treat a failed check command as proof every snapshot is corrupt. | `admin/backup_repository.py:status`, `admin/runtime.py:restore` |
| Per-point verification failure blocks restore | A failed boot/extraction can suppress restoring until verification is resolved. | Distinguish data corruption, incompatible runtime and resource/test infrastructure failure. | `admin/runtime.py:verify_backup/restore` |
| Exact external environment hash required | Changes in service files, bridge, Geyser and relevant config/keys block old points, regardless of semantic compatibility. | Record dependency differences and evaluate compatibility; provide an explicit operator recovery path. | `admin/backup_repository.py:environment/compatible`, `admin/runtime.py:restore` |
| Complete runtime required | Panel refuses incomplete legacy world-only archives for full restore. | Keep completeness checks for full restore; a separate world-only workflow needs its own design. | `admin/runtime.py:preview/restore_archive` |
| Mandatory fresh backup before restore/maintenance | Full repository, damaged live source or failed flush can prevent recovery or maintenance. | Use an independent rollback strategy; allow a reviewed recovery path when the current source cannot be backed up. | `admin/runtime.py:restore_archive/execute` |
| Restore working/rollback directories retained | Old state and staging are kept for operator recovery outside repository budget. | Track separately and garbage-collect after successful recovery and a defined grace period. | `admin/runtime.py:restore_archive` |
| Boot test requires resources and isolation | At least 4 GiB available host memory, complete runtime, private network, bounded CPU/memory/time. | Keep isolation; classify unavailable resources as deferred testing, not corrupt backup. | `admin/runtime.py:verify_backup`, `admin/drill.py` |
| Interrupted restore blocks operations and server start | Journal guard prevents use of a possibly mixed world; manual recovery can be required. | Keep atomicity protection; expose guided reconciliation and allow unrelated metadata/read operations. | `admin/runtime.py:execute/guard_start/recover_restore`, `deploy/systemd/oak-restore-guard.conf` |
| Unknown snapshots are recovered as pinned | Catalog recovery cannot silently delete unrecognized evidence, but accumulated pins may constrain retention. | Temporary recovery hold with visible resolution. | `admin/backup_repository.py:check` |
| Snapshot paths/links/IDs are validated | Symlinks, unsafe archive paths, duplicates, special files and malformed identities fail. | Keep path safety; support valid deployment layouts deliberately rather than bypass checks. | `admin/runtime.py:inventory/inspect_archive`, `admin/backup_repository.py:point` |
| Mixed UI statuses and hidden actions | Pinning, test evidence and integrity share a badge; unavailable restore/delete buttons disappear; refresh is suppressed while focus is inside workspace. | Separate retention metadata from health; show actionable reasons and refresh without disrupting edits. | `public/admin/backups.js` |

## Recommended implementation order

1. Repair backup admission, retention and reclamation as one lifecycle; expose actual time coverage, repository usage and workspace usage separately. Preserve recoverability when a replacement fails.
2. Replace the fixed 12-hour interruption with renewable, revocable device sessions and draft preservation. Correct unnecessary account-update revocation side effects.
3. Separate test evidence from backup availability; replace blanket compatibility/failure gates with target-specific diagnosis and explicit recovery paths.
4. Reduce review dialogs and hidden actions; use capability-based administration and resource-specific scheduling.
5. Retain integrity, path safety, access control, CSRF, isolation, idempotency and interrupted-restore guards, while providing guided resolution.

Retention duration and a fixed disk ceiling cannot both be guaranteed for arbitrary world growth. The implementation must make storage pressure visible and define which objective takes priority instead of silently stopping or promising an impossible minimum history.
